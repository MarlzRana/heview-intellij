heview-intellij — Implementation Plan

A JetBrains-IDE port of reviewa-vscode (being renamed heview): leave inline code-review comments that are injected into Claude Code & Codex via hooks.
Status: Draft for approval · Stack: Kotlin + IntelliJ Platform Gradle Plugin 2.x · Target: all JetBrains IDEs, min 2024.2
This document is the source of truth we align on before any code is written. It captures (1) how reviewa-vscode works today, (2) every decision already made, (3) the target architecture and on-disk contract, and (4) the phased build. Anything marked Later is deliberately deferred out of v1.

1 · Goal & scope

Recreate reviewa's core loop inside JetBrains IDEs, faithful to its semantics but native to the IntelliJ Platform.

The core loop, unchanged in spirit:

  1. Developer clicks a line and leaves an inline comment (GitHub-PR style).
  2. The comment is written to disk as a JSON file under a shared root.
  3. A coding-agent hook (Claude Code, Codex) reads all comments matching the agent's working directory on the next prompt, injects them as context, and deletes the file (single-use, first-come consumption).
  4. heview watches the comments directory, sees the deletion, and flips the thread to Seen / collapses it.

v1 delivers: inline commenting on normal open files, Claude + Codex hook install/registration, consumption watcher, comment tool window, status-bar widget, and settings. Gemini CLI support is removed (deprecated). Diff-view commenting and the Claude plan feature are deferred to later phases.

2 · How reviewa-vscode works today

Understanding the existing semantics precisely is the whole point of this section — the port must preserve them.

Comment controller

Uses VS Code's first-class vscode.comments.createCommentController. A commentingRangeProvider allows comments on every line of file- and git-scheme documents. Threads support multiple replies; each comment shows a Pending / Seen label; the thread shows "Pending comments" or "All comments seen".

Storage

One JSON file per thread at ~/.reviewa/v1/comments/<uuid>.json. In-memory Map<uuid, TrackedComment> is the UI source of truth; the thread's contextValue stores the uuid for reverse lookup. Replies concatenate into a single file's content (joined by blank lines).

Diff-side detection

In a diff, it finds the TabInputTextDiff, then compares the line's text on both sides to classify it as addition / removal / context (file). This drives the +/-/none prefix injected to the agent.

Consumption watcher

fs.watch on the comments dir. A deletion not initiated by the UI (a suppression set guards UI-driven deletes) means a hook consumed it → mark comments Seen, set thread resolved/collapsed if autoCollapse is on.

Hook install / registration

Scripts ship in dist/hook-scripts/<agent>/ and are copied to disk on activation. Registration edits each agent's own config (Claude ~/.claude/settings.json, Codex ~/.codex/hooks.json + config.toml feature flag). Only registers for CLIs found on PATH.

Plan feature (Claude/Gemini)

A PostToolUse:Write hook detects ~/.claude/plans/*.md and writes plan-metadata JSON. A watcher auto-opens the plan and lets you comment on it, routed to Claude via intended_consumer + a logical_abs_path remap. Shown in a Plans tree.

Supporting UI & lifecycle

  • Sidebar (activity bar) with a Comments tree (grouped by file) and a Plans tree.
  • Status-bar item with a custom glasses icon showing the pending count.
  • Editor-title copy buttons to copy pending comments (contextual on plan files, generic elsewhere via a setting).
  • GitHub identity: pulls the signed-in GitHub user + a rounded avatar; falls back to "You".
  • Cleanup: on deactivate (workspace close) it deletes all pending comment files.
  • Platform: Windows unsupported (bash wrappers + Unix paths).

4 · On-disk contract (~/.heview/)

The directory heview-intellij owns. Comments are pooled (so whichever agent runs first consumes them); everything else is separated per coding agent.

~/.heview/
├─ comments/                                          # SHARED pool — one <uuid>.json per thread
│  └─ processed/                                       # hooks CLAIM a comment by moving it here (not
│                                                     #   unlink) so any client can tell consumption
│                                                     #   from a peer/user delete; the tombstone IS the
│                                                     #   consumed comment, rewritten to status=processed
│                                                     #   (restorable), lingering for peers — age-swept
│                                                     #   after 14 days, not eager-deleted
├─ claude-code/
│  ├─ hooks/
│  │  ├─ user_prompt_submit_insert_comments_hook.js   # comment injector (Node)
│  │  ├─ user_prompt_submit_insert_comments_hook.sh   # bash wrapper → node
│  │  ├─ post_tool_use_plan_hook.js                   # (Later) plan detection
│  │  └─ post_tool_use_plan_hook.sh
│  └─ plan-metadata/                                  # (Later) <planName>.json per detected plan
└─ codex/
   └─ hooks/
      └─ user_prompt_submit_insert_comments_hook.py   # comment injector (Python stdlib)

Naming convention: every hook file is <event>_<purpose>_hook.<ext> — no more bare hook.js. The comment injector fires on UserPromptSubmit and inserts pending comments, so it is user_prompt_submit_insert_comments_hook; the plan detector fires on PostToolUse, so it is post_tool_use_plan_hook.

Registration lives outside ~/.heview/, in each agent's own config home (heview only edits these files, it does not own them):

AgentRegistered inEvent → command
Claude Code~/.claude/settings.jsonUserPromptSubmit → bash ~/.heview/claude-code/hooks/user_prompt_submit_insert_comments_hook.sh
Codex~/.codex/hooks.json (+ ~/.codex/config.toml flag [features] hooks = true — codex_hooks is a deprecated alias)UserPromptSubmit → python3 ~/.heview/codex/hooks/user_prompt_submit_insert_comments_hook.py

Changes vs reviewa: the comment injectors are renamed from the generic hook.js / hook.py to descriptive, event-prefixed names (user_prompt_submit_insert_comments_hook.*), matching the post_tool_use_plan_hook.* convention; the injectors also move out of the loose v1/ root into their own <agent>/hooks/ dirs, and every path baked into the wrappers and registration commands is updated to ~/.heview/<agent>/hooks/…. The scripts are otherwise functionally identical — same events, same read/format/delete logic (with COMMENTS_DIR = ~/.heview/comments).

5 · Comment schema & lifecycle

The top-level fields are preserved verbatim from reviewa (so the same hook scripts work unchanged). One file per thread; replies[] is a heview superset field (see below):

{
  "uuid":             "…",             // filename is <uuid>.json
  "status":           "pending" | "processed",  // DERIVED: pending iff any reply is actionable
  "created_at":       "<ISO-8601>",     // DERIVED: bumped on any reply add / edit / re-pend
  "workspace":        "/abs/project/root",
  "abs_path":         "/abs/path/to/file",
  "logical_abs_path": "/abs/path/to/file",  // remapped for plan files (Later)
  "line_number":      42,
  "line_content":     "const x = 1",
  "side":             "file" | "addition" | "removal",  // v1 always "file"
  "content":          "the review comment text",  // DERIVED: the PENDING replies, joined by "\n\n" (hooks read THIS)
  "intended_consumer": "claude_code",   // optional; absent = any agent
  "replies": [                          // heview superset (a foreign/legacy file omits it → 1 reply from content)
    { "content": "…", "status": "pending" | "processed", "author": "…", "created_at": "<ISO>",
      "id": "…" }                        // stable per-reply identity (heview-internal; edit/delete/re-pend match on it)
  ]
}

Why replies[] (heview divergence). A thread is a list of replies, each with its own status and its own edit / delete / re-pend actions — reviewa's per-comment UI, which reviewa keeps only in memory (it is session-scoped). heview is durable (it reloads the pool on restart), so the per-reply structure is persisted. The hook-facing content/status stay derived from replies — content is the PENDING replies joined by a blank line (Seen replies are excluded from injection) — so the injectors are unchanged (they read content and move the whole file on consume). heview-vscode adopts the same field (or ignores it, degrading to one reply).

v1 field simplifications (sanctioned): side is always "file" (diff-side detection deferred); logical_abs_path == abs_path (plan remap deferred); workspace is the IntelliJ project base path, a v1 approximation of reviewa's git-repo root (hooks match by abs_path prefix, so injection is unaffected). Persistence is async/off-EDT (the platform forbids blocking I/O on the EDT) and atomic; line_content is read from the editor buffer at submit.

Per-reply state machine — built

Each REPLY within a thread is independently:
                add reply / edit / re-pend
   (new) ──▶ PENDING ◀───────────────────────── PROCESSED ("Seen")
              │  actions: edit, delete           │  actions: edit, delete, re-pend (↺)
              └──────────── hook consumes the whole thread ──▶ all replies PROCESSED
   • PENDING replies are actionable — their text is joined into the thread's `content` and injected.
   • Editing a Seen reply revives it to PENDING; re-pend (↺, Seen-only) revives it unchanged.
   • Deleting the last reply removes the thread+file; deleting the last PENDING reply of a mixed
     thread keeps the Seen replies visible but drops the file from the injectable pool.
   • created_at (top-level + the touched reply) bumps on add / edit / re-pend (drives ordering).

Built (multi-reply threads). A thread renders as a stack of reply rows, each with its author, a Pending/Seen chip, and icon actions — edit (pencil) + delete (trash) always, re-pend (clock AllIcons.Vcs.History) only on a Seen reply — plus a persistent "Leave a comment" box that adds a new PENDING reply. CommentStore.addReply / editReply / rependReply / deleteReply mutate the reply list, recompute the derived content/status/created_at, and re-persist; a revive first removes the processed/ tombstone (a tombstone for an in-index uuid is the watcher's "Seen" signal — leaving it would let the next reconcile flip the thread back). Consuming the thread (hook) flips all replies to Seen at once. Two-state per reply (no separate "re-pending"): PENDING or PROCESSED, matching the replies[].status enum. Each reply carries a stable id so edit / delete / re-pend target the right one even after a concurrent change flips its status or edits its text (all its other fields are mutable); an id-less foreign reply is backfilled. Deferred: restoring a fully-consumed thread across a restart from its processed/ tombstone (in-session it stays visible and re-pendable); a dedicated thread-level "delete whole thread" button; multiple authors per reply.

Session lifetime — a deliberate divergence: heview comments are durable

reviewa comments are session-scoped; heview comments persist across IDE restarts. This is the one intentional lifecycle change, introduced by the CommentInlayManager increment.
reviewa (VS Code)heview (IntelliJ)
On startup The in-memory store starts empty. The extension never reads the pool on activation — the only readdirSync of the comments dir lives in the hook scripts (agent-side). A comment exists in the UI only if created in the current session. CommentStore.hydrate() reads ~/.heview/comments/*.json into the index on startup, and CommentInlayManager re-renders each as an inlay on the file it belongs to. Comments survive a restart.
On close deactivate() → deleteAllPendingFiles(): every pending file is unlinked, its thread disposed, and the store cleared (commentStore.ts, extension.ts:42). Workspace close purges the pool. No purge. A comment leaves the pool only on explicit Delete, or when an agent hook consumes it (single-use — unchanged from reviewa). Scoped project-close cleanup is a Phase 3 item, and even then will be scoped to the closing project — never reviewa's blanket "delete all pending".
On-disk role A transient IPC channel to the hooks: files exist only for the life of the session. Durable state that also serves as the IPC channel to the hooks.

Why diverge. An inline review note shouldn't evaporate because you restarted the IDE or closed the project overnight — it should wait until the agent (or you) resolves it. Persistence also means a comment left in one session is still injectable from a terminal you open later. This matches how a review comment intuitively "sticks".

Consequence to manage. Because the pool is now durable, a comment stays eligible for injection (hooks match by cwd prefix) across restarts until it is consumed or deleted — it does not self-clear the way reviewa's session purge did. Three mechanisms keep the pool honest: the user's explicit Delete; single-use hook consumption (now a claim-by-move into processed/); and the consumption watcher — built — which flips a thread to Seen when its file is consumed and reclaims the processed/ tombstone. Still pending: scoped project-close cleanup (a stale .json can meanwhile be removed by hand from ~/.heview/comments/).

Multi-client sync — the durable pool can have ≥2 live editors Later

Durability turns the pool into shared live state. heview-intellij, a future heview-vscode (once moved to this model), and the agent hooks can all be open on ~/.heview/comments/ at the same time. Today each editor only hydrate()s once at startup, so a comment created, edited, or deleted in one already-open editor is invisible to the other until it restarts.

Making concurrent editors consistent means generalizing the Phase 3 "consumption watcher" from a delete-only listener into a full pool watcher that reconciles the in-memory index + inlays against filesystem events:

  • CREATE (a peer added a comment) → add the thread and render its inlay in matching editors.
  • MODIFY (a peer edited content/status, or created_at bumped) → re-read the file and refresh the card. Concurrent edits settle as last-writer-wins — acceptable for v1 (files are per-uuid, writes are atomic tmp→rename, edits are rare).
  • DELETE is the hard one — three causes are indistinguishable on a bare unlink: a hook consumed it (should mark the thread Seen), a peer/user deleted it (should vanish silently), or this client deleted it (already handled by reviewa's suppression set). Decided (maintainer) — and now built as a shared four-rule contract: (1) Consume = a hook atomically moves comments/<uuid>.json → processed/<uuid>.json (the tombstone IS the consumed comment, so a later restore action can revive it). (2) Seen = for a uuid a client has in-index, a tombstone present in processed/ → markProcessed. (3) Delete = the pending file vanished with no tombstone → evict. (4) Retention = age-based sweep, never an eager per-client delete. Because the move is an atomic rename, whenever a client observes the pending file disappear the tombstone already exists — and because every live client watches the shared comments/ dir, each reaches the same verdict independently. The tombstone is left in place so a slower peer (e.g. heview-vscode) still sees it; a startup sweep reclaims tombstones older than 14 days. Both store calls are idempotent, so a self-delete the watcher later observes is a no-op — the processed/ move replaces reviewa's suppression set. Single-use: each injector moves-then-emits (emits only files it won the rename for), so two concurrent agents can't double-inject. Still Later: CREATE/MODIFY reconciliation for full multi-client sync (a comment created/edited in one already-open client still needs a restart to appear in another); the renamed VS Code plugin implements the same four rules.

This also matters for the VS Code side: when heview-vscode adopts the durable model, both plugins should share one watcher contract (same events, same tombstone/consumed convention) so a comment created in one and resolved in the other stays consistent.

6 · Hook integration (Claude & Codex)

Scripts ship as plugin resources and are extracted on startup — the IntelliJ analogue of reviewa's esbuild copy step.

Injection semantics (unchanged from reviewa)

On its hook event each script:

  1. Reads cwd from stdin JSON.
  2. Scans ~/.heview/comments/*.json.
  3. Keeps a comment if its intended_consumer is absent or matches this agent, and its match-path (Claude: logical_abs_path || abs_path; Codex: abs_path) is under cwd at a directory boundary (== cwd or starts with cwd + "/"). Divergence from reviewa (sanctioned): reviewa uses a raw startsWith(cwd), so a session in /a/app also matches — and, since injection deletes the file, steals — comments left in the sibling /a/app-backend. heview's boundary check fixes that cross-repo data loss.
  4. Sorts by created_at, formats each block, then claims each emitted comment by an atomic move into ~/.heview/comments/processed/ (rewriting its status to processed) — not an unlink — and emits additionalContext. Divergence from reviewa: reviewa deletes the file; heview moves it so the watcher can distinguish consumption (→ Seen) from a peer/user delete, and the move-then-emit ordering makes it a true single-use claim (two concurrent agents can't double-inject).

Injected block format (byte-for-byte identical to reviewa's Claude hook):

In `src/foo.ts` at line 42:
```
+const x = 1
```
Your comment here

Prefix is + for additions, - for removals, none for context/normal lines. In v1 (files only) this is always no-prefix.

Sanctioned divergence — Codex backtick fix. reviewa's Codex hook (hook.py) copies the JS single-quote escaping '\`' into Python, where "\`" is a backslash plus a backtick — so reviewa's Codex actually injects \`path\` / \`\`\` with literal backslashes, disagreeing with its own Claude hook and with the format above. heview emits clean backticks in both injectors (verified byte-identical between the Node and Python scripts), matching this documented contract. This is a bug in reviewa's src/hook-managers/codex/hook.py worth fixing upstream.

Install & registration (idempotent)

  • Extraction: copy bundled scripts → ~/.heview/<agent>/hooks/, chmod 0755. Overwrite on every startup so upgrades take effect.
  • CLI detection: register an agent's hook only if its CLI is on PATH (which claude / which codex).
  • Claude: append a UserPromptSubmit entry to ~/.claude/settings.json if no existing heview injector is present (dedupe by the injector filename in the command).
  • Codex: Codex hooks are on by default, so heview never edits a present ~/.codex/config.toml (regex-editing arbitrary TOML risks corruption) — it only creates a minimal [features] hooks = true when the file is absent, and warns (touching nothing) if hooks are explicitly = false (hooks or the deprecated codex_hooks). It appends a UserPromptSubmit entry to ~/.codex/hooks.json. Codex also requires the user to trust the hook via /hooks before it runs.
  • Config safety (sanctioned divergence from reviewa): a present-but-unparseable config (bad JSON, non-object root/members, non-UTF-8 TOML, unreadable) is left untouched (warn + skip), never overwritten. reviewa starts fresh on any parse/read failure, which would discard the user's recoverable settings. Writes are atomic (tmp→rename) and follow a symlinked config to its real target.
The dedupe substring changes from reviewa to heview. Because the two products use different roots and different marker strings, a machine can run both side-by-side without their registrations colliding.

8 · Component breakdown (Kotlin)

Domain & storage

  • HeviewComment — data class mirroring the JSON schema.
  • CommentStore (application service — the pool is shared across projects) — in-memory Map<uuid, HeviewComment>, JSON read/write + startup hydrate(), forAbsPath lookup, removable change events; suppression set + scoped cleanup arrive with the watcher.
  • HeviewPaths — central resolver for ~/.heview/….

Inline UI

  • InlayCardHost — thin adapter wrapping the experimental addComponentInlay / EditorEmbeddedComponentManager call; the one-file swap point, with the gutter+popup fallback behind the same interface.
  • CommentInlayManager — recreates/updates/disposes inlays per Editor via EditorFactoryListener (open/split/reopen/close) + a CommentStore change listener (add/delete/status-flip reconciled across splits) + a FileDocumentManagerListener (an external file reload — an agent editing a file to resolve a comment — can dispose the inlays but fires no store change, so fileContentReloaded reconciles the file's open editors to recreate the disposed cards; it trusts the reload-shifted anchors (IntelliJ diffs the reload, so a surviving RangeMarker stays attached to its code — the display card's teardown deliberately does NOT retire the shared anchor, so a recreated card reuses it) and bins an orphaned comment — a reload never invalidates a surviving marker (it shifts it), so the orphan signal is content drift: if a marker's current line no longer matches (trimmed) its comment's stored line_content, the anchor drifted onto different code (the commented line was deleted or externally rewritten) and the comment is store.deleted from the pool (gone for the injector + peers too) rather than left on unrelated code; a marker that merely shifted with lines above keeps the same content and is kept; binning is reload-only (a save's writeback keeps the stored line_content in step, so only an external change diverges) and silent; a shared writeBackAnchors writes each valid anchor's current line back to the pool from BOTH beforeDocumentSaving and fileContentReloaded (in each, the document equals disk) so line_number tracks the on-disk file the agent reads); Disposer-scoped cleanup; EditorScrollingPositionKeeper to avoid scroll jumps.
  • CommentCardPanel — Swing card (author, label, markdown text, Edit/Delete/Reply).
  • AddCommentAction + GutterIconRenderer — entry point to create a thread (also the fallback popup trigger).

Hooks

  • HookInstaller — extract scripts, chmod.
  • ClaudeHookRegistrar / CodexHookRegistrar — idempotent config edits + CLI detection.
  • resources/hook-scripts/{claude-code,codex}/… — the shipped scripts.

Watch & surfaces

  • CommentsPoolWatcher — NIO WatchService on the pool → mark Seen / evict. Built (consumption slice + shared tombstone contract, hardened through a 5-cycle /aeview-loop): on a comments/*.json ENTRY_DELETE, a matching file in processed/ means an agent hook consumed it (→ markProcessed; the tombstone is left for peers + restore, age-swept after 14 days) vs a bare vanish → evict. A one-shot reconcile (after startup hydrate + on OVERFLOW) catches missed events (marks Seen; safe-evicts only on OVERFLOW, gated on a persisted-uuid set); the daemon self-heals if the pool dir is removed at runtime. Full CREATE/MODIFY multi-client sync is Later.
  • HeviewToolWindowFactory + tree model.
  • PendingCountWidget (status bar).
  • HeviewSettings + HeviewConfigurable.

10 · Non-goals & risks

Explicit non-goals for v1

  • Gemini CLI (removed entirely).
  • Diff-viewer commenting (Phase 4).
  • Claude plan feature + Plans view (Phase 5).
  • Renaming/repointing the VS Code plugin (separate task).
  • Windows support (bash/python wrappers + Unix paths; macOS/Linux only, matching reviewa).

Known risks / things to validate early

  • Interactive inlays are the right call — but on an experimental API. Research (against the SDK docs + intellij-community source) confirmed a live-Swing block inlay (Editor.addComponentInlay; older entry EditorEmbeddedComponentManager) is the only path that meets the always-visible interactive-card bar, and it is exactly what JetBrains' own GitHub-PR/GitLab/Space review comments ship on — production-proven, not exotic. The genuine risk is that these APIs are @ApiStatus.Experimental / platform-impl and have drifted between versions (EditorEmbeddedComponentManager.Properties constructor changes have caused NoSuchMethodError in third-party plugins). Mitigation: isolate the call behind a one-file InlayCardHost adapter; confirm addComponentInlay exists on the 2024.2 baseline (use EditorEmbeddedComponentManager there if not); smoke-test across a couple of IDE builds; keep the fully-stable gutter + JBPopup component-popup as a drop-in fallback.
  • Don't depend on com.intellij.collaboration directly — its editor-inlay utilities (renderInlays, CodeReviewComponentInlayRenderer) are Experimental/Deprecated and coupled to JetBrains' coroutine-ViewModel model. Copy the pattern (anchor at getLineEndOffset(line), relatesToPrecedingText(true), FIT_VIEWPORT_WIDTH, scroll-keeper) — do not call it.
  • Anchoring & lifecycle — inlays follow their document offset across in-IDE edits automatically (like a RangeMarker), but are per-Editor and not persisted: recreate them on editor open/split via EditorFactoryListener, translating the stored line_number → offset, and dispose per editor. The persisted line number stays the injection anchor (as in reviewa), but is refreshed on save: beforeDocumentSaving writes each anchor's current line/line_content back to the pool (via CommentStore.updateLocation), so the durable line_number matches the on-disk file the agent reads. Save-gated on purpose — an unsaved edit leaves the pool alone (the agent still reads the old on-disk file, so the two stay consistent). On an external file reload, IntelliJ diffs the new text (common-affix trimming in replaceString), so a surviving marker is correctly shifted and is trusted; fileContentReloaded only reconciles to recreate cards the reload disposed. A reload never invalidates a surviving marker — it shifts it — so a comment is treated as orphaned only on content drift: when the marker's current line no longer matches (trimmed, so a re-indent is tolerated) the stored line_content, the anchor has drifted onto different code (its commented line was deleted or externally rewritten) and the comment is binned (store.deleted from the pool) rather than left on unrelated code. Binning is reload-only and silent: a save's writeback keeps the stored line_content in step with in-IDE edits, so only an external change diverges (an in-IDE line deletion stays undoable until the file is reloaded from disk). It is deliberately conservative — a false bin deletes a comment for every client — so only a valid marker, on a still-pending comment, with a non-blank baseline is binned: an invalidated marker is kept (a both-ends reload — a change at the top and bottom of the file — replays as one whole-middle replaceString that invalidates untouched middle markers, so binning them would mass-delete), and a consumed/Seen thread is kept (an agent resolving a comment consumes it and rewrites the line).
  • External-dir file watching — WatchService reliability varies; keep a polling fallback.
  • Config-file edits — must be idempotent and preserve unrelated user config in settings.json / hooks.json / config.toml.

11 · Testing & dogfooding

Three loops, fastest to most real. The load-bearing insight: the agent CLIs and the hooks live outside the IDE sandbox, so the entire pipeline is dogfoodable from day one — even from inside runIde.

Gradle tasks

TaskPurpose
./gradlew runIdeLaunch a sandboxed IDE with heview loaded — the VS Code "Extension Development Host" equivalent. Sandbox state under build/idea-sandbox/, isolated from your daily IDE. Runnable in debug for breakpoints.
./gradlew buildPluginProduce the installable build/distributions/heview-*.zip.
./gradlew testJUnit unit tests over pure logic (store, hook install/registration, schema, watcher) against a temp HOME — no running IDE. Mirrors reviewa's vitest suite.
./gradlew verifyPluginJetBrains Plugin Verifier across the range of target IDE builds — the safety net for the experimental inlay APIs (§10). Catches NoSuchMethodError-class drift at build time, not at a user's desk.

Loop 1 · Inner loop (runIde)

Edit Kotlin → stop → runIde again. A fresh sandbox IDE each time; nothing touches your real IDE config. Launch in debug from the Gradle tool window to hit breakpoints inside the plugin. This is the fast iteration loop.

Loop 3 · Daily dogfood (install-from-disk)

buildPlugin → Settings → Plugins → ⚙ → Install Plugin from Disk → point at the zip. heview now runs in the IDE you actually work in, against real projects and real agent sessions. This is how you live on it.

Loop 2 · Full end-to-end, from the sandbox

Because heview writes to real ~/.heview/ and registers in real ~/.claude/settings.json / ~/.codex/hooks.json — and because claude/codex are terminal tools that run outside the IDE — the whole loop works without leaving runIde:

  1. runIde → open a project, leave a comment → JSON lands in real ~/.heview/comments/.
  2. In that project (easiest: the sandbox IDE's built-in terminal, so cwd == the comment's workspace) run claude/codex and submit a prompt.
  3. The hook injects the comment as context and deletes the file.
  4. heview's watcher sees the deletion → flips the thread to Seen (and collapses it if configured).
Isolation knob. Loop 2 touches your real agent config. For a throwaway environment, point both sides at the same disposable home — the IDE via runIde { jvmArgs("-Duser.home=/tmp/heview-dev") } and the CLI via HOME=/tmp/heview-dev claude. They must agree: the plugin resolves user.home, the hook scripts resolve $HOME. For everyday use, just use your real $HOME — registration is idempotent, heview-marker-scoped, and fully separate from reviewa's ~/.reviewa/ + reviewa markers, so the two coexist without collision.
